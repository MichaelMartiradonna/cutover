# Cutover

[![tests](https://github.com/MichaelMartiradonna/cutover/actions/workflows/tests.yml/badge.svg)](https://github.com/MichaelMartiradonna/cutover/actions/workflows/tests.yml)

Every system migration has the same weak point: the CSV export from the old system. It arrives with blank keys, dates in two formats, a status value nobody documented, and a duplicate row that someone "fixed" by hand last year. If that file is loaded as-is, the problems become the new system's problems, and nobody can say afterwards which rows were trusted or why. Cutover is a small, fail-closed toolkit for that handoff: it validates the export against rules a human has agreed to, renames and reorders columns into the target layout without touching a single value, checks the result against the source (row count, key set, non-null counts, and field-by-field equality for every mapped column, after both files pass their checksums), optionally uploads it to S3 and verifies what landed, and leaves a run directory with reject logs, reports, and SHA-256 checksums for sign-off. When any stage fails, nothing usable is written. It rejects; it never repairs.

```text
 legacy export            rules/<name>.yaml           mappings/<name>.yaml
 (source.csv)                   |                            |
      |                         v                            v
      +--------> [1] validate.py --------> [2] map.py ---------> [3] reconcile.py --------> [4] upload_s3.py (optional)
                  rejects.csv              target.csv            reconciliation.md          upload_report.md
                  clean.csv                target.csv.sha256     rows, keys, non-null,       local hash == remote hash
                  clean.csv.sha256         mapping_report.csv    field equality: PASS/FAIL
                       |                        |                     |                           |
                   exit 1 = rejected        exit 1 = refused       exit 1 = FAIL              exit 1 = mismatch
                   (no clean.csv)           (no target.csv)        (report only)              (report only)

 exit 0 at every stage + a signed RUNBOOK.md = go.  Anything else = no-go.  Exit 2 = the run itself failed; use nothing from it.
```

Requirements: Python 3.10+ and `pip install pyyaml` (the only dependency; `boto3` is needed only for the optional upload stage). Commands below are PowerShell, run from the folder containing `validate.py`. Everything in `data/` is fictional; the files under `data/examples/` are generated by `tools/make_examples.py`, and `data/accepted.csv` and `data/fake_tenants.csv` are the original hand-written fixtures.

### Optional: upload with verification

The last stage needs `pip install boto3`, a bucket you own, and credentials in the environment or an AWS profile (never a file in this repository). It uploads `target.csv`, downloads it again, and compares the SHA-256 of what came back with `target.csv.sha256`:

```powershell
python upload_s3.py "$run/reviewed/target.csv" s3://YOUR-BUCKET/cutover/parts/target.csv --out "$run/reviewed"
"Exit code: $LASTEXITCODE"
Get-Content -LiteralPath "$run/reviewed/upload_report.md"
```

Exit 0 and `Verdict: PASS` in `upload_report.md` (bucket, key, sizes, sidecar, local and remote hashes) mean the object in S3 is byte-identical to the file you reconciled. A mismatch exits 1 and the report says not to use the remote object. If the object already exists, the stage refuses (exit 2) rather than overwrite it. This stage was not part of the proof run above because it needs an AWS account; `tests/test_upload_s3.py` exercises it against a mocked S3 (`pip install "moto[s3]"`) and against an in-memory stub that needs nothing.

Sign-off for a real cutover follows [RUNBOOK.md](RUNBOOK.md): pre-checks, dry run, go/no-go criteria, a sign-off block that records the run directory and checksums, and rollback.

## What it refuses to do

- Fill a blank, guess a status, reinterpret a date, trim whitespace, or change case. Values pass through byte for byte or the file is rejected.
- Release the good rows from a rejected file. One bad row blocks the whole clean export; review happens in a separate input copy, then the entire file is rerun.
- Merge or drop duplicates. Every member of a duplicate group is rejected and the log names the other records.
- Apply a mapping that leaves a source column unaccounted for, a target column without a source, or a constant that is not declared as a quoted string. There are no transforms or expressions in a mapping.
- Map or compare a file that is not what the previous stage wrote: `clean.csv.sha256` and `target.csv.sha256` must be present and must match, or the stage exits 2 without a report.
- Load a rules or mapping file with an unknown key, a missing key, or a column name that is not in the header. Configuration problems exit 2 before any output exists.
- Overwrite anything: a previous run directory, `target.csv`, `reconciliation.md`, `upload_report.md`, or an existing S3 object.
- Read credentials from the repository, or ship real data. All example data is fictional and seeded.
- Offer a force-pass flag, a quiet mode that hides a rejection, or a summary that could be mistaken for approval.

## Reference

The sections below are the detailed contract. [checks.md](checks.md) is the reviewed rule specification and [architecture.md](architecture.md) explains execution, outputs, and fail-closed handling across the pipeline.

### Validation stage (`validate.py`)

`python validate.py SOURCE.csv --rules rules/<name>.yaml --out NEW_DIRECTORY` validates one CSV against a rule set, blocks the handoff if any check fails, and otherwise writes an unchanged clean CSV plus a checksum. With no `--rules`, it loads `rules/tenants.yaml`, which holds the original five tenant checks:

1. **Required unit:** reject blank or whitespace-only units.
2. **Required name:** reject blank or whitespace-only names.
3. **Valid non-future date:** require an exact, valid `YYYY-MM-DD` date no later than today.
4. **Allowed status:** accept only `active`, `notice`, or `vacant`.
5. **Duplicate unit+name:** reject every member of a duplicate pair, comparing without surrounding whitespace or case differences.

A rules file has exactly these keys: `header` (the exact column list), `required`, `dates` (each `{field, max: today}`), `enums` (each `{field, allowed: [..]}`), `unique` (lists of columns that together must be unique), and `encoding: utf-8-no-bom`. Unknown keys, missing keys, unsupported values, or a rule naming a column not in `header` exit 2 at load time with a clear message. The rule IDs below are fixed by the validator, whatever the rules file says.

Use fictional data only. Requires Python 3.10+, PowerShell, and `pyyaml`; no accounts. The three blocks below use the original small fixtures and the default rules; run them in order in the same PowerShell session, from the folder containing `validate.py`. Each run creates a fresh output directory.

Local viewer, after the accepted example: `python viewer.py "$acceptedOut"` — open the printed local address; press Ctrl+C to stop.

### Talk track

Cutover checks a CSV against explicit, reviewed rules before a handoff, maps it into the target layout without changing a value, and compares what came out with what went in, field by field. Reviewed checks decide. The scripts flag. They do not invent a fix. Any validation failure blocks the entire clean export. A passing input is preserved byte for byte and accompanied by a checksum, and every later stage carries that checksum forward.

### Rules and output contract

- **Required fields (`R001`):** each blank or whitespace-only value in a `required` column gets its own rejection.
- **Date (`D001`, `D002`):** each `dates` column must be an exact ASCII `YYYY-MM-DD` valid calendar date. Blanks, surrounding whitespace, timestamps, and impossible dates fail `D001`. A parsed date after the machine's local date fails `D002`; today passes. The run captures today once and skips the future-date check when parsing fails.
- **Enum (`E001`):** each `enums` column must exactly equal one of its `allowed` values; blanks, different case, and surrounding whitespace fail.
- **Duplicates (`U001`):** for each `unique` column list, compare the tuple of `value.strip().casefold()` when every member is nonblank. Reject all members and identify their conflicting record numbers. Comparison normalization never changes output values.
- **CSV format (`F001`):** UTF-8 without BOM, commas, standard double-quote quoting, and exactly the `header` from the rules file. Reject invalid encoding, missing/wrong headers, and malformed quoting; never guess columns.
- **Records (`F002`, `F003`):** reject a header-only file; require exactly as many fields per data record as the header has. Skip field checks for records with the wrong field count.
- **Checksum (`C001`):** SHA-256 of the written clean file's bytes, stored as 64 lowercase hexadecimal characters, two spaces, `clean.csv`, and one LF newline. `map.py` writes `target.csv.sha256` in the same format.

Accepted input is preserved byte for byte, including names, whitespace, quoting, line endings, and record order. There is no separate name-formatting check. A matching checksum verifies consistency with the stored hash; human review establishes whether source facts are correct.

The mixed example's seven-rejection expectation assumes a local date on or after `2020-01-15` and before `2099-01-01`; the two larger examples assume a local date on or after `2026-06-28` and before `2099-01-01`.

### Mapping stage (`map.py`)

`python map.py RUN/clean.csv --mapping mappings/<name>.yaml --out RUN` reads the validated clean file (its `clean.csv.sha256` sidecar must sit next to it and must match) and writes `target.csv`, `target.csv.sha256`, and `mapping_report.csv` into the same run directory. A mapping file has `source_header`, `target_header`, `columns` (each `{from, to}`), optional `constants` (each `{to, value}` with a quoted string value), and optional `drop` (source columns deliberately left behind). It renames, reorders, drops only what is listed, and adds only declared constants. `target.csv` is written with LF line endings and minimal double-quote quoting; the values inside are the source values unchanged. `mapping_report.csv` has one row per target column (`kind` is `rename` or `constant`) plus one per dropped column (`drop`), with the data-row count. If the mapping is incomplete or the input is not the validated clean file, the stage exits 1 and the report holds `error` rows explaining why; no `target.csv` is written. Schema problems in the mapping file exit 2 before anything is written.

### Comparison stage (`reconcile.py`)

`python reconcile.py RUN/clean.csv RUN/target.csv --key COL[,COL] --mapping mappings/<name>.yaml --out RUN` first verifies both files against their `.sha256` sidecars (a missing, malformed, or mismatching sidecar is exit 2 with no report: a file that changed after its stage wrote it is never compared), then compares them on data-row count, the set of key values (the key names source columns; with a mapping the target columns are looked up, without one the columns are paired by shared name), the per-column non-null count, where non-null means not the empty string (nothing is trimmed), and field-by-field equality: rows are joined on the key and each mapped source value must be byte-identical to its target value, and every constant column must hold exactly the declared value in every row. `reconciliation.md` lists every check with expected, actual, and PASS/FAIL, shows up to 20 missing or unexpected keys and the first 5 differing keys per failed equality check, and ends with a `Verdict:` line. Any FAIL exits 1. A key column that does not exist, a malformed file, or a mapping that does not fit the files is an invocation error: exit 2 and no report. This is a file-to-file comparison of the handoff, not a reconciliation against the receiving system.

### Upload stage (`upload_s3.py`)

`python upload_s3.py RUN/target.csv s3://BUCKET/KEY --out RUN [--profile NAME] [--region NAME]` requires `boto3` (exit 2 with an install hint when missing) and `target.csv.sha256` (exit 2 when missing or malformed). It first checks the local file against its sidecar, refuses to overwrite an existing object, uploads, downloads to a temporary file, and compares sizes and SHA-256. `upload_report.md` records bucket, key, sizes, sidecar, local and remote hashes, and the verdict. A mismatch exits 1. Transport, permission, or credential errors exit 2 and the console says whether the object had already been uploaded.

### Exit codes and troubleshooting

- **0:** every check in that stage passed and all of its outputs were written.
- **1:** the stage rejected its input (validate), refused the mapping or input (map), or found a mismatch (reconcile, upload). Only the log or report is produced; the stage's data output is blocked, including otherwise valid rows.
- **2:** invocation, configuration, or local read/write failure. The run failed; do not use any leftover files from that run. Cleanup after a write failure is best effort and can itself fail, leaving a file behind. Read the console error. An `I001` read/write rejection is logged at row 0 of `rejects.csv` (or as an `error` row in `mapping_report.csv`) when possible; logging failures are reported on the console.

The stages do not print a success summary; the example commands display the exit code and files. Stop if results differ from the expected outcome. `CHECKSUM MISMATCH` exits 1 from the verification command and means the file or stored checksum differs; do not use the handoff.

`validate.py` requires a new output directory for each run, even if a previous directory is empty. The later stages write into that same directory but refuse to run if their own output files already exist there. Existing files are never overwritten. The source file remains unchanged. The examples keep generated output under `output/`, which is ignored by git.

### Local viewer

`python viewer.py RUN_DIRECTORY` reads an existing run and shows clean rows, reject rows with their rule and reason, the stored checksum, and, when present, the mapped target rows, the mapping report, the target checksum, `reconciliation.md`, and `upload_report.md`. Use `$run/reviewed` from the examples as the directory. The single page is served only on `127.0.0.1`; open the address printed in the terminal and press Ctrl+C to stop. Refresh to reread the same directory.

This is a read-only viewer, not a product or a validation run. It does not upload files, edit data, change rules, or verify a checksum. Missing files are labeled. Displayed files do not establish that a run succeeded: exit 2 leftovers must not be used as a handoff.

### Read rejections and rerun

`rejects.csv` has the header `row,rule,why`. The header of the input is CSV record 1; the first data record is 2. Quoted multiline records count once. Row 0 means a file-level error. One record can have several rejections. Malformed quoting stops parsing when record boundaries become unreliable; otherwise the script reports every safely evaluable violation.

1. Find each reported record in the original fictional input. The log identifies problems; it does not supply missing facts or decide which duplicate is correct.
2. Make reviewed corrections in a separate input copy. Resolve every duplicate member explicitly; do not extract a partial handoff from rejected input.
3. Run `python validate.py PATH_TO_REVIEWED_COPY.csv --rules rules/<name>.yaml --out NEW_OUTPUT_DIRECTORY`, substituting the actual paths.
4. Release a handoff only after exit 0 at every stage and checksum verification. Every rerun checks the entire input again.

The toolkit accepts only fictional CSVs shaped by a reviewed rules file. It does not establish source truth, transform accepted values, silently remove rows, or offer a force-pass option.
